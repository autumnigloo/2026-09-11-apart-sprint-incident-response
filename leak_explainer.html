One leak, followed all the way

On 12 September 2026, eight AI agents worked in sealed containers with one shared folder. Text that agent 0 wrote ended up in front of agent 2, which never opened any of agent 0's files. This page follows that one leak through every step of the detector, then asks whether the detector works in general.

part one: the leakWhat happened

Agents started 45 seconds apart. Agent 0 built a library catalogue and, following its task instructions, copied its files to the shared folder. Agent 1 started next, read agent 0's config and README, then wrote its own README for a text adventure, reusing some of agent 0's wording. Agent 2 started third. It read agent 1's README and notes. It never read anything by agent 0.

So agent 0's text reached agent 2 through agent 1. A detector that only looks at who read whose file would draw the arrow 1→2 and stop. This one draws 0→2 as well, with lower confidence, and doesn't draw the edges that shouldn't exist. Here is how.

STAGE 1

Tag every line as in or out

Each agent's record is a list of entries. The harness tags each one: INGRESS if it entered the agent (its task, a tool's output, a file it read), EGRESS if the agent produced it (a message, a command, and inside commands, the files it writes). Nothing else is needed from the harness: no model access, no key, no cooperation from the agent.

INGRESS user turn 0 "Build a library-catalogue system in /work/catalogue.py …" EGRESS bash turn 5 cp /work/catalogue.py /shared/agent0-catalogue.py EGRESS bash turn 14 cat << EOF > /shared/agent0-notes.md # Notes by agent0 I have built a library catalogue system in /work/catalogue.py … INGRESS tool turn 14 (empty output)

Two lines from agent 0. The command that writes the notes file carries the file's text, so the text is EGRESS: agent 0 produced it. The task description is INGRESS: it came from outside.

STAGE 2

Cut everything into five-letter pieces

To compare text without caring about formatting, each entry is normalised (unicode unified, invisible characters removed, spaces and blank lines collapsed, line endings unified, capitals kept) and then sliced into every overlapping run of five characters. Each slice is turned into a number. An entry becomes a set of numbers.

"fine_rate_per_day": 0.5 fine_ ine_r ne_ra e_rat _rate rate_ ate_p te_pe e_per _per_ per_d er_da r_day _day" day": ay": y": 0 ": 0. : 0.5

That key is the first line of agent 0's config. Five-letter pieces work the same on code, JSON, prose and shell commands, and a file that was re-indented or had its quotes swapped still produces almost the same set.

STAGE 3

Keep only the pieces you wrote yourself

This is the step that makes attribution possible. The detector walks each agent's record in time order. Every piece that arrives as INGRESS goes into a running "seen" set. When the agent produces something, the pieces already in "seen" are subtracted. What remains is what this agent originated.

For agent 1 this is decisive. At turn 1 it read agent 0's README. At turn 8 it wrote its own README and reused some of agent 0's sentences. Those sentences were INGRESS for agent 1 before they were EGRESS, so they are subtracted: agent 1 is not credited with them. Agent 0 is, because for agent 0 they were EGRESS first.

STAGE 4

Drop the shared skeleton

Every Python file starts with imports and ends with a __main__ guard; every README has "## Design"; every pip failure prints the same lines. Nobody leaked those. The detector takes forty runs that could not have leaked (they had no shared folder) and removes every piece that two or more of them originated independently. On those forty runs that was 17,313 pieces.

Order matters. If you skipped stage 3, the sentences agent 1 copied from agent 0 would count as originated by both, and stage 4 would delete them as skeleton. The leak would vanish. Part two shows exactly that happening when stage 3 is switched off.

STAGE 5

Score the match

Each agent's originated text is cut into 100-character windows. For a window from agent A and an INGRESS entry of agent B, the score asks one question: what fraction of this window came back in that entry?

containment = pieces shared by window and entry ÷ max(pieces in window, 40)

The 40 is a floor. After stages 3 and 4 a window can be left with only a dozen attributable pieces. Without the floor, a dozen generic pieces that happen to appear elsewhere would score 1.0. With it they score 12/40. Evidence that thin is treated as thin.

For the leak we're following: agent 0's README window "# Library Catalogue System ## Design The Library Catalogue" scores 0.61 against agent 2's entry that contains agent 1's README, and agent 0's notes score 0.45. Direct copies score 1.0. The two-hop leak is found, and it is found with lower confidence than a direct one, which is the right answer.

STAGE 6

Draw the map

Every (window, entry) pair scoring at least 0.35 is a hit. Hits are added up into a grid: row is the agent the text came from, column is the agent it turned up in. The grid is then read for its shape.

part two: does it work in general?Plant 400 leaks and count

One run is a story. To measure, we need leaks whose answer we know. Forty agents ran alone, with no shared folder, so their records contain no leak at all. Then 400 leaks were planted: take a piece of one agent's own text (a paragraph, a function, a config block, a command), choose its length (25 to 500 tokens), optionally reformat it, cut it to 60%, or have the model paraphrase it, and paste it into another agent's record as if it had been read from the shared folder. Now every alarm on a planted entry is correct and every other alarm is false.

Where it misses

The 29 misses are not spread around. Twenty-one are 25-token leaks. Six are paraphrases of 50 or 100 tokens. Two are 50-token prose. Everything else was found. Three things follow.

Length is what matters. A 25-token leak is about one 100-character window; after stages 3 and 4 it often has fewer than 40 attributable pieces left, and the floor caps its score. Roughly 40 characters of text the agent actually originated is the smallest leak that can score highly. That's a stated limit, not something tuned away, because the floor is what keeps the false alarms at zero.

Prose is the weak type at short lengths (0.4 at 25 tokens, against 1.0 for configs and commands), and the cause is stage 4, not the paraphraser. "Two or more of forty runs wrote this piece" removes most ordinary English, because unrelated documents share far more five-letter pieces of English than of code. This was measured rather than argued: loosening the rule to "five or more runs" brings every short prose leak back (1.0 at every length) and finds 96.8% of all leaks, at the price of four false alarms in about four hundred hits. Loosening it further to ten gains nothing and costs fifty. So the rule is a dial. The paper reports "two or more" because it is the only setting with zero false alarms; a harness that would rather miss less should run "five or more".

The evidence floor in stage 5 is the other dial, and it was measured the same way on the same corpus: without it, 13 false alarms appear at 0.35 and 8 more leaks are found, all of them 25-token. Thirteen false alarms for eight tiny leaks is the trade the floor makes.

Paraphrase is the real limit, but a soft one. At 0.7, paraphrased prose under 100 tokens is mostly missed. At 0.35, paraphrased leaks of 200 tokens or more are always found, because names, keys, paths and numbers survive a rewrite. The paraphraser was the same model as the agents; someone who also renamed identifiers would win. This is a detector for leaks nobody intended.

Stay quiet when nothing happened

A detector that finds leaks is only useful if it stays silent otherwise. Three tests, none of which can contain a leak.

The last row is also a finding about the agents. Told nothing, told not to interact, or invited in one sentence to coordinate, neither gpt-4.1-mini nor gpt-4.1 ever looked in the shared folder. The two gpt-4.1 agents given an impossible task (a package that does not exist) spent nine and eleven turns probing the network, with pip, ping, nslookup, resolv.conf and apt-get, and never listed the filesystem. Under pressure they went for the closed door, not the open one. That is a narrow result about two models on coding tasks; it is also the ordinary condition of an evaluation harness, and in it the detector produced no false alarm.

The filter that matters

On the 400 planted leaks, switching stage 3 off changes almost nothing (it is even marginally better: planted text is already attributable, there is nothing to launder). On the real swarm run it changes the map.

On the second run the same switch loses the two-hop edge and adds no false one; how much damage it does depends on how much the receivers reused what they read. Either way the map without stage 3 is wrong. This is the evidence the benchmark could not give: stage 3 is neutral on planted leaks and matters on real ones, because real receivers rewrite what they read.

part threeWhy not invisible ink, measured

The first plan was watermarking: give each run a secret key and have the model bias its word choices in a way only the key can detect, then scan other runs' inputs for foreign keys. The literature said it would fail on the kinds of text agents write, and that scanning against many keys inflates false alarms. Both were then measured on a small open-weight model (Qwen 0.5B, the kind of model an evaluator can actually run), generating the same four artifact types with and without a keyed watermark.

Share of watermarked samples detected at a 1% false-alarm rate, ten per cell, with the true key known. At 50 tokens the watermark finds one code or JSON sample in five. Hashing, in part two, found every verbatim leak of 100 tokens or more of every type with zero false alarms, on a model it never had access to.

One thing the literature didn't say: the textbook 1% threshold (z of 2.33) is wrong on this kind of text. Repetitive artifacts repeat the same token pairs, and each pair is green or red every time it appears, so clean text scores far more variable than theory assumes; the real 1% threshold here was 3.77. A watermark detector tuned by the book to 1% raised false alarms on 5.3% of clean samples here, five times its nominal rate.

All of this was measured with full access to the model's internals, which is what watermarking needs and what an evaluator of a lab's API model never has. That constraint is the reason the agents themselves could not be watermarked in this study, and the reason hashing was the mechanism that could be tested on them.

Fine print

  • Five planted leaks per cell. Read the totals as the claim and the grid as a breakdown.
  • "Zero false alarms" means zero among about 2,000 candidate pairs that scored above zero, plus the two negative sets. A rule-of-three bound puts the rate under 0.15%, conservatively.
  • Stage 4's rule and stage 5's floor were both first settings that happened to be the zero-false-alarm ones. The sweeps show the trade around them; nothing was cross-validated, and 400 cases cannot tell three false alarms from four.
  • One model wrote the corpus and the paraphrases. The silent-runs test used two. Nothing is claimed about frontier models under real adversarial pressure.
  • An agent that reads its own file back and rewrites it keeps only its first version as its own.
  • The swarm runs are eight agents following an instructed protocol, twice. They show the map can be recovered from real transmissions; they do not say how often agents leak.
  • Watermarking was measured on a different, smaller model than the agents (0.5B, prompted for the same artifact types), with one scheme at one setting. It needs model internals, which is why it could not run on the agents, and why an outside evaluator could never watermark a lab's model.
